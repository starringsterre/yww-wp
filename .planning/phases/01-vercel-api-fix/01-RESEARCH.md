# Phase 1: Vercel API Fix - Research

**Researched:** 2026-03-07
**Domain:** Vercel serverless deployment, esbuild bundling, Express 5 on Vercel
**Confidence:** HIGH

## Summary

The core problem is well-understood: Vercel's serverless function runtime only bundles files inside the `api/` directory. The project's Express server code lives in `server/` and `shared/`, so `api/[...all].ts` cannot import `../server/index` at runtime on Vercel. The `includeFiles` vercel.json option is ignored because the project uses the Vite framework preset.

The solution is verified: use esbuild to pre-bundle `server/index.ts` (plus all its dependencies from `server/` and `shared/`) into a single `api/_server.mjs` file during the build step. The `api/[...all].ts` catch-all then imports from this local bundle instead of crossing directories. A test run confirms esbuild produces a clean 17.7KB ESM bundle with all project code inlined and npm packages kept external.

`serverless-http` is no longer needed because Vercel natively supports `export default app` for Express apps as serverless functions. The body parsing concern (Vercel auto-parsing vs Express middleware) applies only to raw `api/` functions, NOT when exporting an Express app as default -- Express handles its own middleware chain.

**Primary recommendation:** Add an esbuild step to `npm run build` that bundles server code into `api/_server.mjs`, update `api/[...all].ts` to import from `./_server.mjs` and export the Express app directly, remove `serverless-http`, pin Node.js 22.x.

## Architecture Patterns

### Recommended Project Structure
```
api/
  [...all].ts          # Catch-all: imports _server.mjs, exports Express app
  _server.mjs          # GENERATED by esbuild (gitignored) -- bundled server code
server/
  index.ts             # Express app factory (source of truth)
  routes/*.ts          # Route handlers (Klaviyo integrations)
  lib/klaviyo.ts       # Klaviyo API client
shared/
  api.ts               # Shared types
```

### Pattern 1: esbuild Pre-Bundle in Build Step
**What:** Run esbuild during `npm run build` to produce `api/_server.mjs` from `server/index.ts`
**When to use:** Every build, both local production build and Vercel build
**Example:**
```bash
# Add to package.json scripts:
"build:api": "esbuild server/index.ts --bundle --platform=node --format=esm --packages=external --outfile=api/_server.mjs"

# Update build script to include it:
"build": "npm run build:client && npm run build:server && npm run build:api"
```

### Pattern 2: Express Default Export for Vercel
**What:** Export the Express app directly from `api/[...all].ts` -- no serverless-http wrapper needed
**When to use:** The only pattern for Vercel serverless Express
**Example:**
```typescript
// api/[...all].ts
import { createServer } from "./_server.mjs";
export default createServer();
```
Source: Vercel official docs (https://vercel.com/docs/frameworks/backend/express)

### Pattern 3: Node.js Version Pinning via engines
**What:** Add `engines.node` to package.json to pin Node.js 22.x
**When to use:** Always, for reproducible builds
**Example:**
```json
{
  "engines": {
    "node": "22.x"
  }
}
```
Source: Vercel docs (https://vercel.com/docs/functions/runtimes/node-js/node-js-versions)

### Anti-Patterns to Avoid
- **Cross-directory imports from api/:** Never import `../server/...` from `api/` files -- Vercel does not bundle files outside `api/` when using the Vite framework preset
- **serverless-http wrapper:** Adds unnecessary complexity and has proven incompatible with Express 5 on current Vercel runtime
- **includeFiles in vercel.json:** Ignored by Vercel's Vite framework builder; does not work for this project setup
- **Removing `import "dotenv/config"` from server/index.ts:** Harmless on Vercel (no .env file present); needed for local `npm run start` production mode

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Bundling server code | Custom Rollup/Webpack config | esbuild one-liner | 19ms build, zero config, already available as Vite dependency |
| Express-to-serverless adapter | Custom request/response translation | Vercel native Express support (`export default app`) | Vercel handles the adapter layer internally |
| API function per route | 8 separate `api/*.ts` files | Single catch-all with Express router | Routes are already defined in Express; catch-all preserves existing architecture |

**Key insight:** The entire fix is about build tooling, not application code. The Express server works perfectly -- it just needs to be bundled into a single file that lives inside `api/`.

## Common Pitfalls

### Pitfall 1: dotenv/config import in bundle
**What goes wrong:** `import "dotenv/config"` in the bundle tries to load a `.env` file that doesn't exist on Vercel
**Why it happens:** The import is in `server/index.ts` for local development
**How to avoid:** This is actually fine -- dotenv silently does nothing when no `.env` file is found. Do NOT remove it, as it's needed for `npm run start` (local production mode).
**Warning signs:** None expected -- this is a non-issue, but flagged because it looks like it could be a problem.

### Pitfall 2: Body parsing double-parse
**What goes wrong:** Vercel automatically parses `request.body` for raw serverless functions. If Express middleware also parses, the body stream is already consumed.
**Why it happens:** Vercel adds helper properties to the Node.js request object.
**How to avoid:** This does NOT apply when using `export default app` with Express. Vercel routes the raw HTTP request through Express, which handles its own middleware chain. The body parsing middleware in `server/index.ts` works normally.
**Warning signs:** POST requests returning empty body or parse errors.
**Confidence:** HIGH -- the existing minimal Express test function (api/test.ts) with Express body parsing worked on Vercel.

### Pitfall 3: esbuild output not in .gitignore
**What goes wrong:** `api/_server.mjs` gets committed to git, causing unnecessary diffs
**Why it happens:** It's a generated file in a tracked directory
**How to avoid:** Add `api/_server.mjs` to `.gitignore`
**Warning signs:** Large diffs in PRs from generated code

### Pitfall 4: Forgetting to run build:api before deploy
**What goes wrong:** Stale or missing `api/_server.mjs` on Vercel
**Why it happens:** The esbuild step is not part of the build pipeline
**How to avoid:** Chain it into the existing `"build"` npm script. Vercel runs `pnpm build` (configured in vercel.json `buildCommand`).
**Warning signs:** "Cannot find module './\_server.mjs'" errors in Vercel function logs

### Pitfall 5: CORS wildcard in production
**What goes wrong:** Current `app.use(cors())` allows all origins
**Why it happens:** Default cors() configuration is permissive
**How to avoid:** This is a Phase 3 concern (HARD-02). For Phase 1, the focus is on making it work at all. The wildcard CORS is acceptable for now since all API routes require authenticated Klaviyo API keys server-side.
**Warning signs:** None for Phase 1; security hardening is deferred.

## Open Questions

1. **Express 5 default export compatibility with Vercel**
   - What we know: Vercel docs show Express 4 examples; Express 5 was tested with a minimal standalone function and worked fine
   - What's unclear: Whether there are any edge cases with Express 5's routing changes that affect Vercel's adapter
   - Recommendation: The esbuild bundle + `export default app` approach should work identically to the minimal test function that succeeded. Deploy and verify with `/api/ping` first.

2. **Vercel's default Node.js version change to 24.x**
   - What we know: Vercel now defaults to Node.js 24.x for new projects; this project should use 22.x
   - What's unclear: Whether the existing Vercel project is already on 24.x or still on an older default
   - Recommendation: Pin `"node": "22.x"` in package.json `engines` to ensure consistency with the existing `target: "node22"` in vite.config.server.ts. Can be changed to 24.x later after testing.
